# SoDam 자동 조율·경험 개선 사용법 (0.3.0)

## 기본 검증 절차 자동 저장 보강

승인된 프로젝트에서 manage_workflow의 verified finish가 의미 검수 확인, 실제 파일 검사, 성공 실행 기록 및 미해결 오류 없음 조건을 통과하면 lesson 생략 시 한국어 기본 검증 절차를 자동 저장한다. 원문·요청·산출물 내용은 경험에 복사하지 않는다. failed/unverified에는 기본 lesson을 만들지 않는다. 기존 사용자 지정 lesson과 완료된 과거 경험은 보존하며, 다음 dispatch는 같은 분야·역량의 증거를 다시 검사한 뒤 최대 3건만 반환한다. 이것은 고정된 검증 절차 재사용이며 전문 지식 자동 추출, 새 역할의 효과, 모델 재학습을 증명하지 않는다. 직접 CLI finish/record는 필요한 lesson을 명시해야 한다.

## 목적과 실행 범위

기존 10개 전문팀·사용자 스킬 관리에 선택형 `autonomy-team`을 추가했다. 설치 후 Codex가 관련 스킬을 선택하고 Node 컨트롤러로 프로젝트별 조율·경험·후보·시험 적용·복귀를 관리한다. 모델 가중치 재학습이나 별도 서비스 생성은 하지 않는다.

**설치·활성화·스킬 선택·컨트롤러 실행·실제 업무 효과는 별도 단계**다. 설치나 전역 설정 변경은 검증 단계와 분리한다. 훅은 정의별 사용자 신뢰가 필요하며 코드가 신뢰 설정을 우회하지 않는다. 새 Codex 대화에서 자동 선택되는지, 실업무 품질이 좋아지는지, 외부 프로그램 연계가 되는지는 별도 실사용 검증이 필요하다. 컨트롤러는 실행 권한을 강제하는 OS 샌드박스가 아니다.


## 0.3.0 훅 자동 연결과 재사용

설치 후 `/hooks`에서 실제 훅 정의를 검토하고 신뢰한다. 정의 변경 뒤에는 다시 검토한다. 공식 동작 설명: https://learn.chatgpt.com/docs/hooks . 훅 설치·신뢰·실행·업무 적용·품질은 각각 확인한다. 공개 플러그인 디렉터리의 훅 허용 정책과 GitHub/로컬 설치는 구분한다.

SessionStart는 산출물 해시가 유효한 최근 성공 절차 최대 3개를 반환한다. UserPromptSubmit은 승인된 프로젝트에만 turnKey와 실제 설치 스킬 경로를 제공한다. 모델은 관련 스킬을 읽고 `dispatch`를 호출하여 계획·생성 역할·관련 경험을 업무에 적용한다. PostToolUse는 도구 ID 해시와 알려진 실행/실패/미확인 상태만 기록하며 응답 원문을 저장하지 않는다. `finish`는 taskId·역할·측정 시간을 연결한다. 성공에는 알려진 도구 실행과 실제 산출물, 미해결 실패 없음이 필요하다. 도구 응답 형식을 알 수 없으면 미확인으로 남긴다.

Stop은 같은 세션에서 정확한 자체 후속 메시지를 한 번만 원래 작업에 연결한다. 두 번째 종료·도구 실패·사용자 중단은 반복 실행하지 않는다. 성공을 추정해서 기록하지 않는다. 다른 정상 요청은 별도 작업이다. 훅 오류는 보고하고 연결이 확인됐다고 주장하지 않는다. 기존 훅은 함께 실행될 수 있으므로 다른 훅/프로필과의 실제 충돌 시험이 필요하다.

```powershell
node "실제 설치 위치/runtime/cli.mjs" dispatch "프로젝트 경로" request.json
node "실제 설치 위치/runtime/cli.mjs" finish "프로젝트 경로" result.json
node "실제 설치 위치/runtime/cli.mjs" recall "프로젝트 경로"
```

```json
{"turnKey":"훅이 제공한 32자리 해시","kind":"docs","goal":"저장한 안내서를 실제 명령과 대조"}
```

finish: `{turnKey,outcome,cause,evidence,corrections,lesson?}`. 단순 요청은 `skip`에 `{turnKey,reason:"simple-query"}`를 전달한다. 중단된 작업은 강제로 재개하지 않는다. 실패 도구가 있는 작업은 보수적으로 verified를 거부하므로 이력을 지워 통과시키지 않는다.

lesson과 cycle의 선택 입력 spec은 `{objective,procedure,checks}`다. 한 줄 문구 400자 이내, procedure 2~8개 `{action,detail}`, checks 1~5개다. action은 inspect-requirements / inspect-environment / read-reference / apply-existing-skill / use-authorized-tool / compare-artifacts / verify-output / review-rights / report-limits 중 선택하며 verify-output을 포함한다. 원문 지시·셸 명령·URL·권한 우회를 넣지 않는다. 제한된 문구도 의미적 지시 주입을 완전히 판별할 수 없으므로 업무 자료로만 읽고 상위 지시와 실제 도구 권한을 따른다.

프로젝트 `.sodam-agent/hooks.json`은 최소 실행 이력이며 개인 기억·계정 전체 학습 데이터가 아니다. 역할 후보는 반복 실패 2개와 구조 검사 뒤 pilot으로 생성되며 실제 효과 확정은 기존 방식과 서로 다른 2개 새 작업의 쌍별 비교를 요구한다. 지속 개선은 다음 승인된 요청에서 이어진다. PC 종료 중 실행·자동 모델 훈련·무제한 역할 생성·독립 품질 인증을 제공하지 않는다.

## 시작하기

1. 이 마켓플레이스에서 필요한 기존 팀과 `autonomy-team`을 설치한다. 이는 선택형이다.

```powershell
codex plugin add autonomy-team@sodam-agent-codex
```

2. 새 Codex 대화에서 실제 프로젝트를 지정해 “이 프로젝트에서 자동 조율·경험 개선과 필요한 역할의 시험 적용을 사용해줘”라고 요청한다. 그 프로젝트에 대한 사용자 승인만 적용하며 이전 프로젝트 승인을 재사용하지 않는다.
3. 관련 작업에서는 `autonomy-team` 스킬이 `runtime/cli.mjs`를 호출한다. 아래 명령도 직접 사용할 수 있다. CLI는 요청을 쉘 인자로 조합하지 않고 프로젝트 안의 JSON 파일을 읽는다.

```powershell
node plugins/autonomy-team/runtime/cli.mjs initialize "C:/path/to/workspace" init.json
node plugins/autonomy-team/runtime/cli.mjs plan "C:/path/to/workspace" plan.json
node plugins/autonomy-team/runtime/cli.mjs status "C:/path/to/workspace"
```

`init.json`은 해당 workspace 안에 저장한다.

```json
{"authorize":true,"autoPilot":true,"days":7,"maxAgents":8,"maxExperiences":200,"maxRetries":1}
```

`autoPilot:true`는 새 후보의 프로젝트 내 시험 적용에 대한 사전 승인이 있을 때만 사용한다. 기본값은 false다. 만료되거나 한도에 도달하면 실패로 멈춘다. 기존 승인을 덮어쓰거나 한도를 자동 확대하지 않는다.

`plan.json` 예시:

```json
{"taskId":"guide-one","kind":"docs","goal":"설치 안내서를 작성하고 실제 명령과 대조","excludedKinds":["marketing"],"attempt":0}
```

kind: web, docs, research, data, marketing, security, devops, support, pm, localization, archviz, cad, comfyui. 자동 라우팅은 **Codex가 의도로 정한 kind → 컨트롤러의 확정된 팀 매핑**이다. 키워드 출현만으로 요청 의도를 판정하는 자동 분류기는 아니다.

## 실제 업무와 기록

계획 결과의 관련 스킬을 읽어 작업하고 사용 가능한 도구를 실제 호출한다. 파일 소유권을 나누지 않은 병렬 편집은 하지 않는다. plan이 서브에이전트 생성 권한을 부여하지 않으며 현재 사용자·상위 지시가 우선한다.

record JSON 예시:

```json
{"id":"result-one","taskId":"guide-one","kind":"docs","outcome":"verified","cause":"none","evidence":["outputs/guide.md"],"seconds":120,"corrections":1}
```

- outcome: verified / failed / unverified.
- cause: none / missing-role / environment / permission / quality.
- 필요할 때 안전한 `gap` 식별자와 컨트롤러가 만든 `agent` 이름을 넣는다.
- verified는 기존 프로젝트 안의 실제 파일 증거를 요구한다. 파일 해시·존재를 확인하지만 내용의 사실성·시청·청취·수용을 자동 인증하지 않는다.
- seconds·corrections·outcome은 작업자가 보고한 값이다. 독립 측정이라고 표현하지 않는다. 결과 원문, 개인 정보, 토큰, 고객 자료를 경험에 복사하지 않는다.
- 관련 도구 호출의 최소 증거는 별도 프로젝트 파일에 저장하되 원문 비밀정보를 포함하지 않는다.

```powershell
node plugins/autonomy-team/runtime/cli.mjs record "C:/path/to/workspace" result.json
```

## 경험 → 후보 → 시험 적용 → 효과 판정

서로 다른 2개 taskId에서 **missing-role 실패**가 같은 kind·gap으로 확인돼야 새 후보를 만들 수 있다. 환경·권한 실패 때문에 역할을 증식하지 않는다. 먼저 기존 역할 재사용·조합을 검토한다.

```json
{"kind":"docs","gap":"artifact-proof"}
```

```powershell
node plugins/autonomy-team/runtime/cli.mjs cycle "C:/path/to/workspace" cycle.json
```

cycle은 유한한 한 번의 상태 전이만 수행한다. 후보가 없으면 생성하고, 닫힌 템플릿·출처를 검사하며, autoPilot이 허용된 경우 pilot을 활성화한다. 활성 역할이 있으면 증거를 평가하고, 확정 역할에 새 실패가 없다면 그대로 유지한다.

후보는 임의 실행 코드·새 MCP·권한을 만들지 않는다. 기존 팀을 사용하는 제한된 역할 지시서다. `.sodam-agent/roles/<name>/SKILL.md`에 저장하고 컨트롤러의 registry에서 선택한다. Codex dispatcher가 해당 경로를 직접 읽는다. `.agents/skills`나 개인 스킬 폴더에 설치하지 않아, 비활성 역할이 호스트 자동 탐색으로 다시 선택되는 일을 피한다.

상태: candidate → template-checked → pilot → confirmed, 실패 시 disabled. evaluate는 템플릿·수명주기 검증이며 실업무 행동 검증이 아니다. confirmed에는 발견용 실패 사례와 다른 2개 taskId의 **동일 작업 기존 방식과 후보 방식의 쌍별 비교**, 실제 증거 해시, 시간·수정 횟수 비악화와 최소 한 지표의 개선이 필요하다. 의미·권리·설계·판매 품질 검수는 별도다.

실패한 pilot은 비활성화하고 기존 팀으로 돌아간다. 다음 관련 cycle에서 새 버전은 요구사항-산출물 체크리스트와 증거 검토 단계를 보강한다. 이는 **제한된 절차 개선**이며, 임의의 코드를 스스로 작성·배포하거나 무제한으로 지식을 학습하는 기능은 아니다. 다음 버전도 pilot부터 다시 평가한다.

## 복귀와 한계

```json
{"agent":"docs-artifact-proof-v1"}
```

```powershell
node plugins/autonomy-team/runtime/cli.mjs rollback "C:/path/to/workspace" rollback.json
```

역할 파일·경험은 복구·감사용으로 남기고 dispatcher 선택을 비활성화한다. 원본 프로젝트나 사용자 스킬을 삭제하지 않는다. OS 종료·파일 교체 오류·동시 처리 충돌에서는 실패 후 중단한다. lock이 남았다고 무조건 강제로 지우지 않는다. 프로세스 종료 여부와 상태·역할 파일을 확인하고 복구해야 한다. 만료 승인 갱신이나 경험 한도 정리는 수동 검토 대상으로 남겼다.

Windows·POSIX 경로 이탈·symlink/junction을 검사하지만, 같은 사용자 권한의 다른 프로세스가 검사 직후 경로를 바꾸는 경쟁까지 막는 보안 격리는 아니다. 신뢰하지 않는 워크스페이스에서 실행하지 말고 OS/Codex 권한 경계를 함께 사용한다. 상태 파일은 자격 증명 저장소가 아니며 암호화되지 않는다.

다음 작업 요청 때 재개하는 지속 개선이며, 상시 예약 실행기가 없다. 자동 역할 로드·외부 프로그램 실행·모델 응답 품질·실제 비용은 현재 로컬 시험으로 확인되지 않았다. Node 26 Windows 시험과 CI 설정 검사는 실행했으나 실제 Linux/macOS·Node 20/22 실기기 시험은 별도다.

## 보호 규칙

- 현재 사용자·상위 지시, 명시적 제외·중단, 도구별 승인·볼트 쓰기 게이트를 우선한다.
- 생성된 역할은 재귀 생성·권한 확대·개인 기억·전역 설정·AGENTS 수정·모델 변경을 하지 않는다.
- 링크를 따라 원본 트리를 수정하지 않고 기존 파일·동명 역할 디렉터리를 덮어쓰지 않는다.
- 실패를 숨기거나 기준을 낮추지 않는다. hash 대조를 실제 품질 검토라고 표현하지 않는다.
- 프로젝트의 경험과 승인 파일을 공개 배포하지 않는다. 개인 O-Brain·WikiMate 저장은 별도의 직접 요청과 기존 도구 규칙을 따른다.

## 새 Codex 대화 시험 결과 (2026-10-09)

별도 ephemeral Codex CLI를 읽기 전용으로 실행했다. 프로세스는 종료 코드 0이었으나 파일 읽기 exec_command가 실행 정책에 거부돼 controller_actually_called=false로 보고했다. 따라서 새 대화의 실제 역할 선택·컨트롤러 호출은 통과로 계산하지 않았다. 실행 정책·기존 설치의 frontmatter 오류·일부 외부 MCP 인증 오류는 현재 사용자 환경 문제로 기록하고 전역 설정·플러그인·권한을 변경하거나 우회하지 않았다.

## 중간 검증 보강 (2026-10-09)

초기화·등록 중 잡을 수 있는 저장 오류는 이번 시도에서 생성한 내용이 그대로인 경우에만 recovery-state 또는 recovery-role로 보존하여 재시도를 허용한다. 기존 상태·수동 파일은 교체하지 않는다. 프로세스 강제 종료, 복구 파일 이동 실패, 다른 프로세스의 동시 변경은 자동 복구 보장이 없으며 상태를 점검해야 한다. 복구 파일은 자동 삭제하지 않는다.

CLI 오류는 입력 본문·키·경로를 출력하지 않고 고정 오류 분류만 반환한다. 요청 JSON은 1,000,000바이트, 상태 JSON은 4,000,000바이트까지 읽으며 초과 시 중단한다. 자격 증명 형태의 식별자, 문자열이 아닌 작업 분야, 비활성 역할이나 다른 gap의 역할에 대한 기록을 거부한다. 저장된 산출물의 내용 자체를 비밀 탐지·의미 품질 검수한 것은 아니다.

## 배포 전 검증 보강 (2026-10-09)

Windows의 대소문자 경로 별칭도 내부 상태 증거에서 제외한다. 50자까지 허용된 gap으로 역할 이름이 50자를 넘으면 작업 분야와 gap의 SHA-256 앞20자 및 버전으로 이름을 구성한다. 원래 gap은 역할 내용과 상태에 보존한다. 기존 짧은 역할 이름은 그대로 유지한다.

## 0.3.5 실제 산출물 검증 도구

읽기 전용 MCP `sodam-output.verify_artifacts`에 `{workspace,evidence}`를 전달합니다. 명시적으로 승인된 프로젝트의 상대 경로 1~4개만 검사합니다. md/txt/json/csv/html/svg, 파일당 1~262144바이트, 비어 있지 않은 UTF-8만 허용하며 숨김·민감 경로, 연결 파일, 알려진 비밀정보 형태, 승인 만료를 거부합니다. 결과는 크기·SHA-256·실행 상태이며 내용은 반환하거나 저장하지 않습니다. 동시 외부 파일 교체에 대한 완전한 격리는 보장하지 않습니다. 알려진 형태 검사만으로 모든 비밀정보 부재를 보장하지 않습니다.

실제 결과를 다시 읽고 의미·요구사항을 검수한 뒤, 이 도구의 성공 응답이 훅에 기록됐을 때만 verified finish를 시도합니다. 도구 미연결·미실행·실패는 unverified/failed로 남깁니다. 평문 명령 출력의 성공 문구를 실행 상태로 해석하지 않습니다. 실패 이벤트가 있는 요청의 verified 거부는 유지합니다. 문서 검증은 코드 테스트·시각/청취 검수·새 역할의 개선 효과 증명을 대신하지 않습니다.

MCP 실행에는 Node.js 20.18.1 이상이 필요합니다. 플러그인의 cwd를 기준으로 고정된 runtime/mcp.mjs만 시작합니다. 글로벌 설정·개인 기억·원본 파일을 수정하는 도구가 아닙니다. 새 설치의 실제 Codex 연결·자동 호출·다음 대화 재사용은 별도 사용 시험에서 확인해야 합니다.

## 0.3.4 옵션 입력과 기록 보존

gap은 생략하거나 유효한 식별자 문자열을 전달합니다. excludedKinds는 생략하거나 지원하는 업무 종류의 배열을 전달합니다. 빈 문자열·0·false·null은 유효한 옵션 값이 아니며, 잘못된 요청은 분류 기록과 경험 상태를 변경하기 전에 거부합니다. 정상 요청의 빈 excludedKinds 배열은 허용됩니다.

## 0.3.3 회상 범위와 역할 무결성

dispatch는 업무 kind와 gap이 일치하는 검증된 경험을 먼저 찾고 최대 3개를 반환합니다. gap 없는 일반 업무와 특정 gap 업무를 섞지 않습니다. SessionStart의 일반 회상은 최근 검증된 경험 3개를 제공하며, 실제 업무 선택 뒤에는 dispatch 결과를 사용합니다. 두 경로 모두 반환할 활성 역할의 파일·해시·정본을 확인하고 변조된 역할은 검토 전까지 회상에 노출하지 않습니다. 실패를 숨기거나 경험·역할 파일을 자동 삭제하지 않습니다.

## 0.3.2 제한된 유지보수

`maintenance-authorize`는 기존 프로젝트 승인 안에서 별도 실행 한도를 설정합니다. authorize:true, maxRunsPerDay(1~24), timeoutMs(100~60000)를 가진 프로젝트 상대 JSON 파일을 전달합니다. 기존 유지보수 정책은 덮어쓰지 않습니다.

`maintenance`는 고정된 로컬 Node 작업자만 실행합니다. 최근 유효 증거 확인, 활성 역할 파일 검사, 실패 역할 비활성화, 반복되는 역할 부족 목록을 반환합니다. 자체 모델 호출·임의 명령·외부 API 호출·후보 품질 확정은 하지 않습니다. 호스트 모델의 시간이나 요금은 이 제한으로 통제되지 않습니다.

실행 횟수는 UTC 날짜 기준이며 실패·시간 초과도 차감합니다. 하루 한도·프로젝트 승인 만료·동시 실행·총 기록 1000건에서 중단합니다. 프로세스가 종료되어 running 기록이 남으면 실제 종료 확인 후 maintenance-recover에 acknowledgeStopped:true와 runId를 전달합니다. 회복해도 실행 횟수를 돌려주지 않습니다. 이력은 자동 삭제하지 않습니다.

예약은 이 명령을 호출하는 별도 실행 환경이 필요합니다. 예약 등록·호스트 훅 신뢰·새 대화 자동 사용은 각각 실제로 확인해야 하며 코드 시험 통과로 대신하지 않습니다. 새로운 역할의 전문 절차는 실제 부족 근거를 검토해 기존 cycle 흐름에 전달하고 다른 사례로 검증합니다. 개인 기억·볼트·전역 설정 자동 쓰기는 확대하지 않습니다.

배포 및 상업적 이용 조건은 저장소 LICENSE, NOTICE 및 README의 권리·외부 서비스 안내를 함께 확인하십시오.

## 0.3.6 구조화된 작업 연결

연결된 sodam-output MCP의 manage_workflow를 사용할 수 있다. 조율 시작은 `{workspace,operation:"dispatch",request:{turnKey,kind,goal,gap?,excludedKinds?,evaluationTaskId?}}`, 완료는 `{workspace,operation:"finish",request:{turnKey,outcome,cause,evidence,corrections,semanticReviewed?,lesson?}}`이다. verified 완료는 semanticReviewed:true와 실제 안전한 산출물 검사, 기존 훅 실행 증거, 실패 없음이 필요하다. 의미 검수의 확인은 호출자 평가이며 독립 품질 인증이 아니다. 기존 CLI 경로도 유지한다. CLI 요청 인자는 JSON 원문이 아니라 프로젝트 안의 JSON 파일 경로다.

새 MCP는 초기 승인 생성·권한 변경·셸 실행·글로벌 설치를 제공하지 않는다. 미등록·중단·승인 만료·잘못된 입력은 거부한다. 소스 설치와 실제 새 대화의 조율 성공은 구분한다. 범위를 지정한 recall({kind})은 세부 gap이 없으면 일반 업무 경험만 반환한다. 다른 종류와 잘못된 세부 값은 계속 거부한다.

## 0.3.7 내부 명령 실패와 전달 성공 구분

MCP 전달이 성공해도 JSON 텍스트 안의 실제 exitCode/exit_code가 실패이거나 timedOut:true이면 실패로 기록한다. structuredContent 및 structured_content도 내부 결과를 우선한다. 원문·표준 출력·오류 내용은 저장하지 않는다. JSON 텍스트 검사는 블록4개·블록당64KiB·기존 깊이 제한 안에서만 수행하며, 범위를 넘는 응답이나 잘못된 종료 코드는 unknown이다. 실패·미확인 상태를 성공으로 바꾸거나 이력을 지우지 않는다. 이 변경은 모든 도구의 임의 문자열 출력이나 실제 의미 품질을 자동 판정하지 않는다.

## 0.3.8 대화별 실행과 비교 과제 연결

dispatch에 선택적인 evaluationTaskId를 추가했다. 일반 작업은 기존 turn 기반 taskId를 유지한다. 사전 설계한 기존 방식/후보 방식 비교는 동일한 evaluationTaskId로 eval- taskId를 공유하되 대화별 turnKey·경험 ID·도구 증거·측정 시간은 독립 기록한다. 식별자는 1~40자 소문자·숫자·단일 하이픈이다. 같은 ID의 kind·gap·목표 해시가 다르면 거부하며 목표 원문은 저장하지 않는다. 기존 journal의 새 필드가 없으면 기존 turn 기반 ID를 사용한다.

입력 자료와 수용 기준이 동일한지 별도 확인해야 한다. 같은 ID는 의미 품질 인증이 아니며 기존의 서로 다른 2개 held-out 과제·쌍별 기존 방식 증거·산출물 해시·시간/수정 횟수 비악화·최소 한 지표 개선 조건을 유지한다. 실제 역할 개선 효과와 Desktop/CLI 자동 호출은 별도 실사용 검증 대상이다.

## 0.3.9 Windows MCP 설치 폴더 잠금 해소

Windows에서 MCP가 시작되면 프로세스의 현재 위치만 Node 실행 파일의 상위 폴더로 옮긴다. 설치 캐시를 작업 위치로 유지하면 실행 중인 MCP가 폴더 교체를 막을 수 있기 때문이다. 모듈 로드는 모듈 기준 경로를 유지하고 프로젝트 작업은 승인된 절대 경로만 허용한다. 시작 위치 이동 실패 시 고정 오류로 종료한다. 훅 정의와 권한은 변경하지 않는다. 이전 코드를 실행 중인 MCP는 별도 재연결이 필요하며 다른 채팅 연결을 임의 종료하지 않는다. 살아 있는 별도 MCP의 테스트용 폴더 교체와 이후 파일 검사·작업 기록을 회귀 검증한다. 이 검사는 실제 Desktop 사용자 입력 훅이나 역할의 실제 품질 향상을 인증하지 않는다.

## 작업 중 학습 연결 (0.3.9 로컬 개선)

새 기본 dispatch는 learnWhileWorking:true이다. 작업 모델은 결과·사용자 수정에서 제한된 전문 절차를 추출해 verified finish.lesson으로 전달한다. 실패 교정 가설은 failed finish.reflection으로 분리하며 semanticReviewed:true와 실제 안전한 파일 증거가 필요하다. 환경·권한·미확인 결과는 역량 학습으로 채택하지 않는다. 과거 방식 호출은 고정 기본 교훈 저장을 유지하되 전문 학습으로 간주하지 않는다.

finish/다음 dispatch가 증거·상태·한도를 확인하여 반복된 실제 역량 부족의 역할 생성/시험 활성화, 쌍별 실작업 비교 평가, 실패 복귀를 자동 연결한다. 역할 생성은 프로세스 생성이 아니라 실행 모델이 읽고 적용하는 프로젝트 한정 절차이다. generatedAgent의 실제 읽기·도구 실행·산출물 확인은 모델 책임이며 마커/파일 존재로 성공을 선언하지 않는다. 같은 근거의 재생성, 환경 실패에 의한 전문 역할 비활성화, 비교 증거 없는 개선 확정을 막는다. 생명주기 오류는 adaptation.deferred로 분리해 작업 기록을 보존하며 다음 관련 요청에서 재검토한다.

Codex 예약은 사용하지 않는다. 작동에는 열린 호스트의 요청 실행이 필요하며 종료된 PC/모델 없이 계속 동작한다고 주장하지 않는다. 개인 기억·다른 프로젝트·볼트·전역 설정은 자동 쓰기 대상이 아니다. 기존 경험과 보호된 원본을 보존하며 새 비용·권한을 부여하지 않는다.

## 기존 역할의 품질 교정 개정

비활성화된 같은 kind/gap 역할이 있으면, 기존 생성 근거에 사용하지 않은 서로 다른 작업의 품질 실패와 실제 파일 증거·제한된 교정 절차를 이용해 다음 개정 후보를 만든다. 최초 역할 생성은 반복된 missing-role 증거를 유지한다. 기존 역할 파일은 덮어쓰지 않으며 개정 후보도 pilot이다. 권한·환경 오류, 변조된 증거, 생성 한도는 개선 근거 또는 자동 우회 대상이 아니다. lifetime 생성 한도에 도달하면 새 개정을 자동 생성하지 않는다.

## 학습 선택·품질 비교·운영 상태 보강

회상은 동일한 교훈을 중복 반환하지 않고 같은 범위의 최근 최대24개 성공 기록에서 최대3개의 서로 다른 유효 교훈을 찾는다. 동일 목표의 서로 다른 절차가 있으면 lessonSelection.reviewRequired를 반환한다. 의미상 모순 전체를 자동 판별하지 않으므로 현재 요구·적용 조건을 모델이 대조한다.

finish의 선택 품질 필드 quality:{criteriaId,criteria,passed,errors}는 실제 수용 검수에서만 기록한다. verified는 모든 기준 통과·오류0이어야 한다. 품질이 있는 비교는 양쪽의 동일 criteriaId·기준 수가 필요하다. 필드를 생략한 기존 기록은 보존하며 독립 품질 인증으로 확대하지 않는다.

routing.knownGaps의 기존 식별자는 의미가 같은 경우에만 재사용한다. generatedAgent.relativePath를 실제로 읽고 해시를 확인한 뒤 절차를 적용한다. 역할 적용과 품질 향상은 별도 증거다.

CLI capacity <프로젝트절대경로>는 승인 만료·남은 기록/역할/turn 한도·잠금·열린 작업·보관 대상 해시를 읽기 전용으로 반환한다. 완성된 백업이나 동시 실행 중 일관된 스냅샷이 아니다. 역할/복구 파일까지 완전히 보관·검증한 후 명시 승인된 이관/갱신을 별도 수행해야 한다. 자동 삭제·자동 승인 갱신·이력 이관은 구현하지 않았다.

생명주기 deferred는 민감값 없는 고정 diagnostic으로 누락 파일/권한/저장공간/전제조건을 구분한다. 작업 기록은 보존하며 오류 원문·요청값을 반영하지 않는다.

## 실행 상태 진단과 신규 전문 역할 확정

MCP inspect_runtime({workspace?})와 CLI `node runtime/cli.mjs diagnose <프로젝트절대경로>`는 읽기 전용이다. 승인 없음/만료/미확인, 한도·저장공간·잠금, 열린 작업의 dispatch/read-role/role-step/finish 누락 수를 반환한다. 초기 승인·자동 갱신·삭제·잠금 해제는 하지 않는다. 승인 없는 작업 위치는 SessionStart/UserPromptSubmit에 학습 비활성 안내만 반환하고 기록을 만들지 않는다. 원래 승인된 다른 프로젝트의 정책을 복사해서 연결하지 않는다.

startedAt와 startupSourceFingerprint는 시작할 때 관측한 runtime 소스 파일의 해시다. currentSourceMatchesStartup:false이면 현재 파일과 시작 당시 파일이 다르므로 해당 호스트의 재연결이 필요하다. 실행 메모리의 바이트코드 증명은 아니며, 파일 교체와 기존 프로세스 코드 반영은 구분한다. 새 도구가 발견되지 않는 기존 연결은 이전 코드일 수 있다. 실제 호스트의 도구 호출로 확인한다.

새로 생성하는 전문 절차 후보에는 confirmationPolicy:procedure-quality-v1을 기록한다. 개선 확정에는 서로 다른 held-out 비교 작업 2개, 같은 조건과 품질 기준 정의, 역할 파일 읽기, 모든 절차의 서로 다른 성공 도구 사건과 변하지 않은 산출물 증거가 필요하다. 미흡하면 pilot을 유지하고 작업 기록을 보존한다. 단계 증거와 품질 기준은 호출자 평가이며 독립 전문 품질 인증이 아니다. 이전 정책 표시 없는 역할·경험은 보존하고 legacy-metrics로 구분한다. 전문 절차가 없는 기존 일반 템플릿 경로는 종전 지표 평가를 유지한다.

실제 업무에서 dispatch → 관련 교훈 적용 → 필요 시 read-role/role-step → 산출물 검수 → finish.lesson 또는 실패 reflection 순서로 학습한다. 진단이나 시험 fixture 자체를 실제 경험이나 개선 효과로 채택하지 않는다. 실제 업무 효과는 실제 사용으로만 검증한다. 보관·이어쓰기 안내는 한도에 도달하기 전에 확인하며 승인 만료·실패·동시 실행을 우회하지 않는다. Codex 예약 작업은 사용하지 않는다.

## 승인 작업 영역 자동 연결

사용자가 한 번 명시 승인한 상위 작업 영역 안에서 자동 연결한다. 기존 개별 승인은 독립적으로 유지한다. 정본은 실행 사용자 홈의 `.sodam-agent-areas/registry.json`이며 프로젝트에는 별도의 `.sodam-agent`와 areaBinding만 생성한다. 개인 기억·모델·외부 전송·유료 API·파일 삭제·샌드박스 권한 확대 승인이 아니며 OS와 Codex의 파일 쓰기 권한은 별도로 적용된다.

승인 입력에는 authorize:true, days(1~30), exclusions(존재하는 제외 폴더 절대경로 배열), maxProjects(1~100), maxMutations(1~100000), maxAgents(1~20), maxExperiences(1~1000), maxRetries(0~2), autoPilot(boolean)을 명시한다. 승인할 영역 루트의 입력 JSON으로 `node runtime/cli.mjs area-authorize <영역절대경로> <영역루트상대JSON>`을 실행한다. 명령 실행 전 범위·한도에 대한 사용자 동의가 필요하다. `area-inspect <영역또는프로젝트절대경로>`는 읽기 전용이며 `area-revoke <영역절대경로> <상대JSON>`은 authorize:true, areaId를 받아 취소한다. `connect <프로젝트절대경로>`는 이미 승인된 영역의 표시 파일 있는 프로젝트만 연결한다. MCP에는 영역 승인/취소 도구를 노출하지 않는다.

신뢰된 호스트의 SessionStart/UserPromptSubmit이 승인 영역의 작업 위치를 제공하면 표시 파일이 없어도 그 위치를 최초 연결한다. 하위 폴더는 기존 저장소/AGENTS.md/package.json/git 경계로 프로젝트를 식별한다. 중첩 git은 별도 프로젝트다. CLI/MCP가 제시한 표시 파일 없는 임의 경로를 추측하지 않는다. 시작 훅이 제공한 확정 workspace와 프로젝트 루트 기준 산출물 상대경로를 사용한다. 명령의 cwd에 다른 프로젝트 경로가 등장했다고 채팅의 학습 대상을 바꾸지 않는다.

중앙 잠금 아래 pending → connected로 연결하며 미완성 저장소를 덮어쓰지 않는다. 동시 실행/부분 실패는 학습 미검증으로 보고하고 본래 수행 가능한 업무를 계속한다. 강제 잠금 해제·자동 복구·자동 재시도는 하지 않는다. 영역 기록과 실제 생성 파일을 읽기 전용으로 대조한 후 명시 복구한다. pending도 프로젝트 수에 포함한다. maxMutations는 최초 연결과 파생 프로젝트의 상태 변경 트랜잭션 예약 수이며 실패도 소비한다. 승인/취소와 읽기 전용 조회는 제외된다. 모델 시간·비용 한도나 성공 횟수가 아니다.

제외·보호 폴더·정확한 경로 경계를 검사하고 링크/junction을 거부한다. 디렉터리 실제 식별값으로 이동·대체·복사된 승인의 자동 이관을 막는다. 영역 취소·만료·전체 한도는 파생 프로젝트 쓰기를 차단한다. 개별 continue는 영역 한도를 늘릴 수 없고 저장 전에 거부한다. 기존 개별 승인은 별도로 관리된다. 자동 갱신·자동 한도 확대·기록 삭제·프로젝트 간 교훈 공유는 하지 않는다. 만료/부분 연결/이동 후 재승인·이관은 명시 검토 대상이며 자동 복구로 주장하지 않는다.

이 체계는 신뢰된 로컬 사용자/호스트의 실행 정책이며 같은 Windows 계정으로 승인 파일을 직접 편집하는 공격자에 대한 OS 보안 경계가 아니다. 설치·연결·기술 시험은 실제 업무 자동 호출·학습 효과의 증거가 아니다. 효과는 다음 실제 업무에서 확인하며 예약 작업이나 상시 모델 프로세스는 사용하지 않는다.

## 제한된 코드 문법 검사

실제 업무에서 문법 검사가 필요할 때만 연결된 check_node_syntax에 승인된 workspace와 프로젝트 상대 evidence 1~4개를 전달한다. .mjs/.cjs만 지원하며 고정 Node 파서가 파일 스냅샷을 검사한다. 소스·import를 실행하지 않고 임의 명령·인자·환경변수·작업 위치 변경을 입력받지 않는다. 파일당 256KiB·5초 한도이며 오류 원문과 파일 내용은 반환하지 않는다. .js의 모듈 방식은 추정하지 않는다. 실패·시간 초과·실행 불가는 실패로 보존한다. 문법 통과는 동작·빌드·학습 효과의 증명이 아니다. 기존 Bash 평문 unknown을 이 검사로 소급해서 바꾸지 않는다.

CLI 대안은 syntax-check 프로젝트절대경로 요청파일상대경로이며 요청 파일은 {evidence:[프로젝트상대파일]} 형식이다. CLI 표준출력 자체를 Desktop 종료 메타데이터로 간주하지 않는다. 실제 구조화된 MCP 호출과 의미 검수·verify_artifacts를 구분한다.

## 실행 세대와 운영 판단

MCP는 시작 시 코드 지문과 현재 파일을 대조한다. 변경 또는 읽기 실패 시 manage_workflow의 상태 쓰기를 거부하며 재연결을 요구한다. 진단과 산출물 검사는 별도로 사용할 수 있다. 실행 중인 코드를 자동 교체하거나 승인을 갱신하지 않는다.

고정 문법 검사의 구조화된 성공만 역할 단계의 작업 도구 증거 후보로 인정한다. 도구 이름만 같은 출력, 평문 JSON, 실패, 불완전한 해시 및 경로는 제외한다. 실제 절차 이행과 개선 효과는 추가 결과 검수가 필요하다.

업무마다 승인 만료·동시 실행·저장 한도와 교훈의 근거 해시·현재 적용 조건을 확인한다. 충돌 가능 교훈은 검토하며 의미 충돌 자동 판정을 보장하지 않는다. 한도 도달 시 기록을 삭제하거나 자동 갱신하지 않고 기존 archive/restore 절차를 검토한다. 기술 시험과 실제 경험 및 장기 개선 평가는 구분한다.

## 업무 기반 역할 개선 보강 (0.3.9 로컬 보강)

일반 업무에서 확인된 교훈은 다음 관련 업무에 재사용합니다. 업무를 수행하는 Codex 모델이 기존 절차보다 나은 방법을 실제로 확인하면 bounded lesson에 `improvement: true`를 붙여 개선 후보를 제안할 수 있습니다. 사용자가 매번 이 값을 입력하는 방식이 아닙니다. 이 기능은 모델 가중치를 훈련하지 않고 프로젝트 안의 교훈과 역할 절차를 개선합니다.

- 자동 시험 적용은 기존 프로젝트의 `autoPilot` 승인, 만료일과 역할 한도 안에서만 가능합니다. 승인을 새로 만들거나 자동 갱신하지 않습니다.
- 동일 역량에서 서로 다른 실제 업무 두 건이 같은 개선 절차를 지지해야 합니다. 품질 항목의 정의·작업 맥락·증거 해시가 일치해야 하며, 관련 맥락이 있으면 적용 조건에 포함합니다. 성공 횟수만으로는 후보를 만들지 않습니다.
- 기존 기본 팀의 개선은 프로젝트 전용 역할을 추가하는 방식입니다. 설치된 기본 팀·전역 설정을 덮어쓰지 않습니다. 기존 확정 역할은 절차 실행 증거가 있는 변경 제안으로 새 버전을 만들며, 같은 절차의 반복 생성은 거부합니다.
- 후보는 우선 `pilot`입니다. 생성에 사용하지 않은 서로 다른 두 과제에서 이전 방식과 같은 입력·품질 기준을 비교해야 합니다. 이전 역할의 비교 결과는 새 후보 적용 전에 보존합니다. 품질이 나빠지지 않고 시간 또는 수정 횟수가 개선되어야 `confirmed`로 바뀝니다. 시간·품질 값과 의미 검수는 작업자가 보고하므로 독립 품질 인증은 아닙니다.
- 새 시험 역할이 실패하면 `disabled`로 끄고 이전 검증 역할 상태로 복귀합니다. 파일과 이력은 남깁니다. 기존 명시적 rollback도 사용할 수 있습니다. 임의의 꺼진 역할을 근거 없이 다시 켜는 기능이나 무제한 자기 수정은 제공하지 않습니다.
- 증거 변경·권한 부족·품질 정의 불일치·한도 도달이면 확정하지 않습니다. 실패 반성은 성공 개선 제안과 구분합니다. 자동 처리 오류가 나도 완료 기록을 지우지 않습니다.

관련 구현은 `plugins/autonomy-team/runtime/engine.mjs`, `learning.mjs`, `workflow.mjs`, `bridge.mjs`입니다. 회귀 검증은 `node test/work-learning.mjs`, 전체 검증은 `npm run validate`와 `npm test`입니다. 기술 시험은 실제 새 채팅 자동 실행 또는 장기 업무 개선의 증명이 아닙니다. 설치 파일을 갱신해도 실행 중 MCP는 재연결 전까지 이전 코드를 사용합니다. 예약 작업은 만들지 않습니다.
